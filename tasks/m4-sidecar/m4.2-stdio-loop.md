# M4.2 Stdio loop

- status: done
- depends: M4.1
- files: `sidecar/reader_sidecar/main.py`, `sidecar/reader_sidecar/io.py`, `sidecar/tests/test_io.py`
- goal: A portable line-based stdin/stdout loop that works on Windows too.
- spec:
  1. Read stdin on a daemon thread with `sys.stdin.buffer.readline()`. Push lines into an `asyncio.Queue` via `loop.call_soon_threadsafe`. Do not use `connect_read_pipe`, which is unreliable for stdin on Windows.
  2. Force UTF-8 on both streams. On Windows also set binary mode so `\r\n` is not inserted.
  3. `Writer.send(msg)` takes an `asyncio.Lock`, writes `encode(msg) + "\n"`, and flushes.
  4. Configure `logging` to stderr. Level comes from `READER_SIDECAR_LOG` (default `INFO`).
  5. On startup, send `ready {version}`.
  6. On stdin EOF, close all chats (M4.3) and exit 0. On SIGTERM, do the same.
  7. A malformed line sends `error {kind:"protocol"}` and the loop continues.
  8. Dispatch inbound messages to a `Router` with one handler per type. Handlers are stubs until M4.3.
- done when:
  - [x] Tests drive the loop with in-memory streams: `ready` is sent first, malformed input produces an error and the loop continues, EOF exits cleanly.
  - [x] `echo '{"type":"bogus"}' | reader-sidecar` prints `ready`, then a protocol error, then exits 0.
- verify: pytest plus the shell command above.

- notes:
  - `tests/test_run.py` (implementer-added) covers what `test_io.py` leaves out: `READER_SIDECAR_LOG` levels, SIGTERM with stdin open, stream setup with a faked `msvcrt` on `win32`, `ValueError`/`RecursionError` from `decode`, a failing handler, and cancellation.
  - `decode` can raise `ValueError` (huge integers) or `RecursionError` (deep nesting). The loop answers both, and non-UTF-8 lines, with `error {kind:"protocol", seq:null}`. `protocol.py` is unchanged.
  - A handler that raises gets logged and answered with `error {kind:"internal"}` carrying the message's `chat_id` and `seq`. The loop continues. M4.5 maps SDK errors to finer kinds.
  - SIGTERM cancels the serve task. `serve` runs `router.close()` in a `finally`, then the process exits 0. A second SIGTERM does not interrupt the close.
  - After SIGTERM the stdin thread is still blocked in `sys.stdin.buffer.readline()` and holds that buffer's lock. Normal interpreter shutdown then aborts with `Fatal Python error: _enter_buffered_busy` (exit -6). `run()` calls `logging.shutdown()` and `os._exit(code)` when the reader thread is still alive. atexit handlers do not run on that path.
  - Windows: `setup_streams` sets `O_BINARY` on stdin and stdout with `msvcrt.setmode`. SIGTERM falls back to `signal.signal` because Windows event loops lack `add_signal_handler`. Neither ran on Windows here.
  - An unknown `READER_SIDECAR_LOG` value logs a warning and uses INFO.
  - Out of scope: a write to a closed stdout (`BrokenPipeError`) propagates out of `serve` and ends the process with a traceback. Worth handling when M5.1 wires the app side.
  - human check: run the sidecar on Windows and confirm stdout lines end in a bare `\n` and the bogus-line check exits 0.
