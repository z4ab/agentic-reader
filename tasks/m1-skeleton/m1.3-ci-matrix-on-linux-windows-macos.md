- notes: Pushing needs the user's go-ahead and a GitHub remote. Ask before pushing.
  - carried: (M4.1) `.github/workflows/build.yml` already exists with the `sidecar` job. Add the C++ matrix to the same file.
  - carried: (M1.2 review) `app/CMakeLists.txt` finds `include/poppler/cpp` with `find_path` over default paths. If a runner has system poppler-cpp headers, pin it to the include dir of `unofficial::poppler::poppler-cpp` plus `/cpp`.
  - Blocked: needs push to GitHub. The repo has no remote. The user must add a GitHub remote, push a branch, and check both `done when` lines in the Actions run: all three `cpp` jobs pass with `test_poppler`, and a second run (warm cache) takes under 15 minutes per job.
  - `find_path` left unchanged. The vcpkg toolchain prepends its installed prefix to `CMAKE_PREFIX_PATH`, which CMake searches before system paths and `PATH` prefixes such as `/opt/homebrew`. Locally it resolves to `build/vcpkg_installed/x64-linux/include/poppler/cpp`. System headers could only win if vcpkg's were missing, and then linking `unofficial::poppler::poppler-cpp` would fail too.
  - Binary cache: vcpkg's `x-gha` provider no longer exists (`vcpkg help binarycaching` does not list it), so the job uses the `files` provider in `vcpkg-cache/` with `actions/cache/restore` and `actions/cache/save`. Keys include the run id, restore falls back to the newest cache for the same `vcpkg.json` hash, then the same OS. The job saves only when vcpkg wrote new archives, and it saves after a failed run too, so a port failure on the first run does not discard the ports that built.
  - GitHub caches are branch-scoped: a branch can restore caches from itself and the default branch, not from other branches. The first run on `main` is cold even if a feature branch already warmed its own cache.
  - The cache only grows. Each save holds the old archives plus new ones, so after many `vcpkg.json` changes it approaches the 10 GB repo limit. Consider pruning old archives later.
  - Configure passes `VCPKG_INSTALL_OPTIONS=--clean-after-build` so a cold Linux build fits on the runner disk (a local cold build used 13 GB of buildtrees and 3.5 GB of packages). On failure the job uploads `vcpkg/buildtrees/**/*.log` and `build/vcpkg-manifest-install.log` as `vcpkg-logs-<os>`.
  - vcpkg is cloned at the `builtin-baseline` commit read from `vcpkg.json` instead of using `lukka/run-vcpkg`, so the baseline lives in one place.
  - Ubuntu installs the M1.1 apt list plus `python3-venv`, because the `libsystemd` port creates a Python venv for jinja2. macOS installs `autoconf autoconf-archive automake libtool ninja pkgconf` with Homebrew. Windows uses `ilammy/msvc-dev-cmd` so Ninja finds MSVC.
  - Risk: the first run per OS is cold and may take an hour or more (GTK3 stack on Linux).
  - Risk (Windows): `x64-windows` is a DLL triplet. ctest relies on vcpkg's applocal DLL copy next to the test binaries. Poppler uses the `win32` font backend there, which this project has never built. Long buildtree paths under `D:\a\...` could hit MAX_PATH.
  - Risk (macOS): `macos-latest` is arm64 (`arm64-osx`). Ports that use autotools on macOS (for example gettext-libintl via fontconfig) need the Homebrew tools above. Untested.
  - Risk: `ilammy/msvc-dev-cmd@v1` runs on node20, which GitHub is retiring. If it breaks, replace it with a step that calls `vcvars64.bat` and exports the environment.
